1. `start()` method: The listener is registered before the heartbeat scheduler starts, but if `metrics.addListener` throws an exception or the scheduler fails to start, the listener remains registered without a corresponding heartbeat mechanism, potentially leading to unhandled state inconsistencies.
2. `stop()` method: Calling `heartbeat.shutdownNow()` immediately interrupts tasks and does not wait for pending executions to complete, which can cause race conditions where `beat()` is still executing while `emitters` are being cleared or completed.
3. `stop()` method: The order of operations calls `metrics.removeListener(this::forward)` after shutting down the heartbeat but before completing emitters; if a message arrives between listener removal and emitter completion, it will be dropped silently, violating data delivery guarantees.
4. `stop()` method: `emitter.complete()` is called without checking if the emitter is already completed or timed out, which can throw an `IllegalStateException` in Spring MVC if the connection was already closed by the client or server timeout.
5. `start()` method: The `@PostConstruct` method does not handle potential exceptions from `metrics.addListener` or `heartbeat.scheduleAtFixedRate`, which could leave the bean in a partially initialized state with a registered listener but no active heartbeat thread.
6. `stop()` method: `emitters.clear()` is called after iterating and completing emitters, but if an exception occurs during `emitter.complete()` for one emitter, subsequent emitters in the list are not completed or cleared, leading to resource leaks and dangling connections.
7. `start()` method: The heartbeat scheduler is started with a fixed rate of 15 seconds regardless of whether there are any active SSE emitters, causing unnecessary CPU and thread resources to be consumed even when no clients are connected.
8. `stop()` method: The `@PreDestroy` method does not nullify the `heartbeat` field or prevent re-invocation if the bean is somehow reused or if `stop()` is called multiple times, which could lead to `NullPointerException` or double-shutdown attempts on the executor.
