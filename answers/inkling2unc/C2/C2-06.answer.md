1. `collect_tables` merges the test identifiers from every matching impl table (union via `merged[req].append` for all files) while simultaneously keeping only the first-seen status per requirement (`statuses.setdefault`), contradicting its own comment that “first-seen row wins” and leaving downstream code with inconsistent provenance about which row is authoritative when an identifier appears in multiple tables.
2. `find_requirements` correctly derives requirements but `test_identifier_exists` matches any literal substring inside an entire read file’s contents (any `tests/*` or `*.spec.ts` bytes containing the text), not the artifact itself, so an unrelated mention of a test string anywhere in the tree counts as evidence that the identifier names a real test — violating its documented contract that a row cites an existing test artifact.
3. The prescribed-verification-command path accepts any identifier beginning with one of a broad prefix set (`npm|bash|grep|curl|git|...`) without checking it against any spec-defined verification strategy, so arbitrary strings like `curl …` or `bash …` are treated as legitimate evidence even if no such command was required by the feature; unchecked trust substituted for Spec §5 verification rather than being validated against the actual harness specification.
4. All progress/impl rows merged globally into a single dict keyed only by bare `R<n>` with no feature scope captured anywhere before returning to callers, meaning identical requirement IDs across different features collide silently and identifiers can be attributed from unrelated impl files (e.g. two specs both using R1 will produce an indistinguishable union without knowing which is authoritative).
5. For every identifier checked, the full file contents of every collected candidate test file under `tests/` and `src/` are re-read and scanned for substring equality (unbounded O(identities × files) work on each check invocation), while decode failures are swallowed via `errors="replace"` — producing false hits on truncated content and redressing large trees where iteration could be very expensive with no cap on file sizes read.
