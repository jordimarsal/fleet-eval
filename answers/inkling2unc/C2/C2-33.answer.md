1. connectStream — JSON.parse is not wrapped in try/catch and the unvalidated payload is blindly cast to { seq: number } / StreamFrame, so malformed or ill-typed server data throws inside a listener or produces NaN/invalid seq and corrupted ordering decisions.
2. connectStream — there is no initial baseline handling (lastSeq starts at 0 with lastSeq > 0 required), so an initial gap before the first observed packet is never reported and ordering can be treated as established incorrectly from stream start.
3. connectStream — lastSeq is never reset on reconnect/open after source.onerror sets 'reconnecting', so server sequence restart after a drop makes post-reconnect packets look stale or trigger false gaps relative to the pre-disconnect baseline.
4. connectStream — handlers are invoked even when a forward gap was detected; callers receive onGap but still process the forward frame as if it were cleanly ordered unless they explicitly gate frames on that signal.
5. connectStream cleanup return — the returned close() only calls source.close() with no status transition to a terminal closed state and no removal of onopen/onerror/addEventListener bindings, leaving stale live/reconnecting UI state and retained listener references behind after teardown.
6. Event listener registration in connectStream — every EVENT_NAMES entry registers a separate listener over one shared mutable lastSeq closure without namespaced per-kind expectations, causing duplicate seq updates/gap signals to depend on accidental processing order rather than explicit dedupe keying for each event type.
7. connectStream — hardcoded '/api/v1/stream' URL has no bounded scope for error-status semantics: any error always maps to 'reconnecting' regardless of readyState/terminal failure, masking permanent stream loss from consumers.
