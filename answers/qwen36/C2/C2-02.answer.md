1. `sync()` — Calling `history.replaceState` with an empty title string (`""`) triggers a deprecation warning in modern browsers and may cause unexpected behavior if the browser enforces non-empty titles for state updates.
2. `changed()` — The `render()` call happens before `sync()`, meaning that if `render()` throws an exception (e.g., due to missing DOM elements), the URL will never be updated, leaving stale query parameters in the address bar.
3. `byLabel(lab)` — This function iterates over all entries in `POOL` linearly; since it's called from `sync()` which runs on every change event, this creates O(n) work on every user interaction, potentially causing UI jank as POOL grows.
4. `sync()` — If `selA.value` or `selB.value` is undefined (which can happen during initialization before options are populated), accessing `POOL[undefined]` returns `undefined`, leading to `undefined.s + "," + undefined.t` being encoded into the URL, producing malformed query strings like `?a=undefined,undefined`.
5. `sync()` — The catch block silently swallows errors including potential security exceptions (e.g., cross-origin restrictions when navigating away from file://), making debugging difficult and hiding real failures.
6. `changed()` — There is no debouncing or throttling of the `change` event handler, so rapid successive selections could trigger multiple render+sync cycles unnecessarily.
7. `sync()` — Using `encodeURIComponent` on concatenated values without proper separation means that if a model name contains commas, the parsing logic in `byLabel` will break because `split(",")` cannot distinguish between separators within names versus the intended delimiter.
8. `render()` — Direct assignment to `innerHTML` with unescaped content from `esc(SECTIONS[s][0])` assumes `esc` properly escapes HTML; if `esc` only escapes XML entities but not HTML attributes or other contexts, XSS vulnerabilities may exist depending on what `esc` actually does.
