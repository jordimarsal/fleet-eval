1. `tool_read_file`: The truncation message uses `{path}` which may be an absolute path leaking host filesystem information to the LLM output.
2. `tool_write_file`: Missing `encoding` parameter in `write_text`, defaulting to platform-specific encoding instead of explicit UTF-8 like `read_text`.
3. `tool_edit_file`: Uses `p.read_text(encoding="utf-8")` without `errors="replace"`, so files with invalid UTF-8 sequences will raise `UnicodeDecodeError` instead of returning an error string.
4. `tool_edit_file`: Does not check whether `content > 500_000` before writing, unlike `tool_write_file`, creating an asymmetric API where large edits silently fail later.
5. `tool_edit_file`: If `old` occurs zero times, `text.count(old) != 1` returns True but the error message says "found {text.count(old)}" which reports 0 — this is correct behavior but inconsistent with the docstring intent that should probably distinguish "not found" from "multiple occurrences".
6. `tool_edit_file`: After confirming `old` appears exactly once, it never actually performs the replacement or writes anything back — the function returns nothing (None), making it a no-op despite its name and signature suggesting it modifies the file.
7. `tool_read_file`: Returns truncated content as a plain string rather than signaling truncation explicitly, so callers cannot distinguish between genuinely short files and truncated ones beyond parsing the suffix.
8. `tool_write_file`: Creates parent directories with `mkdir(parents=True)` even when the write fails due to permission errors on the target file itself, potentially creating unintended directory structures in the sandbox.
