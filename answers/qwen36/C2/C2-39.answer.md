1. `EstolApp` - The `nodes`, `statuses`, and other state variables are declared as `var` inside a Composable without using `remember` for their initial values in a way that survives recomposition; if any of these trigger recomposition (e.g., due to parent changes), they will reset to stale defaults, losing user progress and potentially causing inconsistent UI state.
2. `refresh()` - The coroutine launched via `scope.launch` does not handle cancellation properly when the composable leaves the composition tree, which can lead to memory leaks or crashes from accessing disposed state after the scope is cancelled.
3. `refresh()` - The `busy = true` assignment happens before the suspend block completes, but there's no corresponding `busy = false` in a finally block or catch handler, so if an exception occurs during status fetching, `busy` remains stuck at `true`, permanently disabling refresh functionality.
4. `refresh()` - Using `withContext(Dispatchers.IO)` inside a coroutine already running on the main dispatcher is unnecessary overhead since `Fleet.status(node)` likely doesn't require explicit IO dispatching, and wrapping it this way adds latency without benefit.
5. `refresh()` - The `mapNotNull { node -> ... }.toMap()` pattern silently drops nodes where `runCatching` fails, providing no feedback to the user about partial failures, which violates the principle of failing visibly rather than silently swallowing errors.
6. `EstolApp` - `Settings.loadNodes(context)` is called every time the composable recomposes because `remember` only caches based on keys (none provided), meaning settings are reloaded unnecessarily on any configuration change or parent recomposition, causing potential I/O overhead and inconsistent state.
7. `EstolApp` - Multiple independent `var` state variables (`nodes`, `statuses`, `busy`, etc.) should be consolidated into a single state object using `mutableStateOf` with a data class or sealed hierarchy to prevent race conditions and ensure atomic updates across related fields.
8. `EstolApp` - The `showSettings` variable is initialized from `nodes.isEmpty()`, but if `nodes` changes later (e.g., after loading completes), `showSettings` won't update automatically since it's not derived reactively from `nodes`, leading to stale UI behavior.
