1. `stop()`: Calling `heartbeat.shutdownNow()` does not guarantee that the executor has fully terminated before the application context closes, potentially leading to race conditions during shutdown.
2. `start()`: The `heartbeat` scheduler is initialized as a field but lacks error handling; if `this::beat` throws an unhandled exception, the scheduled task will silently stop running for all future intervals.
3. `stop()`: If `emitter.complete()` throws an exception during the loop, subsequent emitters in the list will not be completed, causing potential resource leaks of open connections.
4. `MetricsStreamController`: The `json` mapper and `emitters` list are initialized at the class level but are not marked `final`, which could lead to visibility issues in a multi-threaded environment if they were ever reassigned (though currently only the list is used).
5. `start()`/`stop()`: There is no mechanism to handle the case where `metrics.addListener` or `metrics.removeListener` fails, which could leave the controller in an inconsistent state relative to the metrics source.
6. `MetricsStreamController`: The use of `CopyOnWriteArrayList` for `emitters` combined with manual iteration in `stop()` is safe, but there is no logic shown to remove individual emitters from this list when they time out or encounter errors, leading to a memory leak over time.
