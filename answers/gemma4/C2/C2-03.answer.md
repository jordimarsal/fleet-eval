## Pull Request Review: `graders.py` updates

**Status:** ⚠️ Changes Requested

### Summary
This PR introduces logic for tool-calling evaluation and a centralized system prompt generator for code generation tasks. While the functional logic appears sound, there are several concerns regarding error handling, language support consistency, and documentation standards.

---

### Detailed Feedback

#### 1. `grade_tools` Function

**[Critical] Potential Division by Zero / Logic Error in Score Calculation**
```python
score = sum(1 for r in results if r["passed"]) / len(results) if results else 0.0
return {"passed": score == 1.0, ...}
```
*   **Issue:** If `tasks` is provided but all tasks fail due to `_TRANSIENT` errors, `results` will be populated with failure entries. However, if `tasks` is an empty list, `results` is empty, and you return `score: 0.0`.
*   **Observation:** The `passed` key in the return dict uses `score == 1.0`. This means if even one task fails (or one task hits a transient error), the entire suite is marked as `passed: False`. Ensure this "all-or-nothing" behavior is intended for the benchmarking suite.

**[Minor] Hardcoded Magic Number**
```python
detail[:160]
```
*   **Issue:** You are truncating error details/traces to 160 characters. While this prevents log bloating, it's a magic number.
*   **Suggestion:** Move `MAX_DETAIL_LEN = 160` to a module-level constant to make it configurable or at least explicit.

**[Nit] Unused Argument**
*   **Issue:** `max_turns=6` is defined in the signature but never used within the function body.
*   **Action:** Either implement multi-turn tool calling logic or remove the argument to avoid confusing users.

#### 2. `_code_system_prompt` Function

**[Critical] Language Inconsistency / Missing Support**
*   **Issue:** The docstring mentions "totes les tasques de codi" (Catalan), but the implementation only handles `typescript` and `java`. If a user passes `python`, `cpp`, or `rust`, the `extra` string remains empty.
*   **Risk:** For languages like Python, where indentation is critical, the prompt doesn't explicitly demand specific formatting beyond the fenced block. More importantly, if the benchmark expands, this function will become a massive `if/elif` chain.
*   **Suggestion:** Use a mapping dictionary instead of `if/elif` for better readability and extensibility:
    ```python
    LANG_EXTRAS = {
        "typescript": " You MUST export it (e.g. `export function add(...)`).",
        "java": " Provide the full class with the required method.",
    }
    extra = LANG_EXTRAS.get(lang, "")
    ```

**[Documentation] Language Mismatch**
*   **Issue:** The docstring is written in **Catalan**, while the rest of the codebase (and the code itself) appears to be in **English**.
*   **Action:** Unless `ggufbench` is strictly a Catalan-language project, please translate the docstring to English to maintain codebase consistency.

**[Logic] String Interpolation Bug**
*   **Issue:** 
    ```python
    return ("Reply with ONLY a single fenced ```{l} code block ... {e}"
    ```
*   **Observation:** This is a standard string, not an f-string. The variables `{l}` and `{e}` will be rendered as literal text in the prompt sent to the LLM, rather than being interpolated with the language and extra instructions.
*   **Fix:** Change to an f-string: `return f"Reply with ONLY... ```{lang} ... {extra}"`.

---

### Summary of Required Changes
1.  **Fix the f-string bug** in `_code_system_prompt` (this is a breaking bug).
2.  **Remove or implement** the unused `max_turns` parameter.
3.  **Translate the docstring** from Catalan to English.
4.  **Refactor the `if/elif`** in the prompt generator to a dictionary lookup.
5.  **Verify** if "all-or-nothing" pass logic (`score == 1.0`) is the desired behavior for the benchmark.
