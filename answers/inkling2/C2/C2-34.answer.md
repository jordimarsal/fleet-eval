1. `stop()` uses a freshly constructed bound method reference for removal (`this::forward`) that is not guaranteed to equal the original listener object passed in `start()`, so unregister may silently fail and leave stale forwarders attached to metrics.
2. `heartbeat.scheduleAtFixedRate(...)` runs an unprotected task: if the scheduled work throws, the periodic future is cancelled without restart or logging, leaving keepalives dead while initialization appears healthy.
3. In `stop()`/construction teardown, closing only heartbeats before removing the metrics listener leaves a window where concurrent metric events can run against emitters being completed/cleared, and no await of active scheduled execution gives ordering guarantees during destruction.
4. The `emitters` container has no demonstrated completion-time cleanup tied to emitter closure for ordinary client disconnect; clients can keep state alive beyond their intended lifetime unless this shutdown path constitutes sufficient global finalization after all normal paths are complete.
5. During `@PreDestroy` iteration plus `clear()` exposes race conditions with new/nearby registrations: requests arriving around bean shutdown may add or otherwise act on an emitter between snapshot enumeration and clear, causing incompleteness or duplicate sends instead of a serialized drain.
