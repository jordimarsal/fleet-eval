1. The leading read helper: decoding with `errors="replace"` silently turns invalid bytes into U+FFFD and returns corrupted text as if it were faithful content instead of reporting decode failure.
2. tool_write_file: it checks only that the parent directory has room/length limits, but never verifies the resolved target itself is not an existing directory, so `p.write_text()` raises `IsADirectoryError` instead of returning an error string.
3. tool_write_file: other `OSError`/filesystem failures (disk full, read-only mount, permission on mkdir/write) are uncaught, escaping the expected return-error contract rather than becoming structured ERROR output.
4. tool_edit_file: `old == ""` has Python’s empty-substring semantics (`''.count('') == len(text) + 1`), which can satisfy `!= 1` for an empty file and lets edit bypass normal write validation.
5. tool_edit_file: there is no equivalent cap on `len(new)` while tool_write_file rejects content over 500000 chars, so a small edit can create an out-of-bounds huge file through a different path.
6. tool_edit_file: `read_text(encoding="utf-8")` without replacement handling will raise `UnicodeDecodeError` on non-UTF-8 files, unlike the reader in this same excerpt that tolerates bad bytes, leaving inconsistent behavior and potential crashes.
7. The resolve-then-use pattern across these tools uses `resolve_in_sandbox()` then performs separate filesystem operations with no final handle pinning or race protection against symlink swaps between check and use, making sandbox containment vulnerable to time-of-check/time-of-use races.
