1. `refresh()`: `busy = true` is set but the shown path has no guaranteed reset to `false` or error reporting, so a thrown exception or early exit can leave the UI permanently in the busy state and swallow status failures silently despite an existing `snackbar`.
2. `EstolApp()` initializer / `nodes by remember { mutableStateOf(Settings.loadNodes(context)) }`: synchronous `Settings.loadNodes(context)` runs during composition on the main thread/UI path rather than being loaded asynchronously, blocking recomposition and assuming config reads are cheap.
3. `refresh()` coroutine vs repeat trigger: it does not guard against concurrent invocations (e.g. checking `busy` or cancelling the prior job), so rapid taps can launch overlapping loads that race on `statuses` and stale results overwrite newer ones.
4. `refresh()` mapping of statuses: failed nodes are dropped via `mapNotNull` + `runCatching{...}.getOrNull()`, so unreachable/errored nodes disappear from `statuses` instead of surfacing as errors; duplicate node names would also collapse via `toMap()` with last-wins data loss.
5. `showSettings by remember { mutableStateOf(nodes.isEmpty()) }`: initial value is captured once at first successful read and never recomputed when settings change/reload, so the “auto-open settings when empty” contract becomes stale after nodes are added or removed.
